## Primary learning idea

Recovery of a committed side effect

## Precise task

Record a completion notification intent atomically with job completion. A worker sends it and records delivery state. Inject crashes before send, after send, and before acknowledgement.

## What this teaches

- **transactional outbox:** An outbox stores side-effect intent in the same database transaction as the business change. Example: Commit completion and its notification intent together.
- **at-least-once processing:** At-least-once processing can repeat deliveries, so consumers must tolerate duplicates. Example: A worker crash causes a notification attempt to be retried.
- **idempotent consumers:** An idempotent consumer prevents duplicate deliveries from repeating a business effect. Example: Record a processed operation ID before repeating a stock adjustment.
- **queues:** Queues buffer work for later consumers and need admission, capacity, and failure policies. Example: Hold notification jobs while the provider is unavailable.
- **dead letters:** Dead letters retain work that cannot be processed normally for inspection or recovery. Example: Inspect a repeatedly rejected notification.
- **retry budgets:** A retry budget bounds attempts or time to avoid endless overload. Example: Stop automatic retries after a defined limit and surface the failure.
- **distributed transactions:** Distributed transactions coordinate changes across multiple systems; simpler local transactions do not cover remote effects. Example: A database commit cannot atomically guarantee a third-party notification.
