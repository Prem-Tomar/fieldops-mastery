**Target:** 20–25 hours per week per learner, plus review/coaching. Each week adds an integrated product capability. Dates are targets: narrow the feature slice or extend the schedule if its mastery gate is not passed.

**Learners:** Neha (@Neha2212-vi, 5 years) and Madhavi (@madhavichauhan1995, 10 years). **Reviewer and only merger to master:** @Prem-Tomar.

## Ownership and full coverage

Each learner receives a different implementation ask. Neha initially owns job workflows; Madhavi initially owns inventory workflows. Both work in JavaScript, TypeScript, Node, PostgreSQL, React and React Native, then cross feature boundaries in integration and the capstone. Ownership does not excuse a concept gap.

For **every one of the 338 catalog concepts**, each learner must independently explain the idea, predict behavior, make or adapt a bounded implementation in their own feature or experiment, demonstrate the result, and solve an unseen variation. Reading the peer's PR or attending a shared demo alone does not pass the concept. Use the individual ledgers for [Neha](../evidence/learner-5y/coverage.csv) and [Madhavi](../evidence/learner-10y/coverage.csv); experience never waives basics.

Production code is implemented once per capability. Reuse accepted functions and shared contracts; a second learner contributes another feature, not the same function under another filename. Short disposable experiments may repeat a concept when needed for individual assessment; they are not duplicate product tasks. Weekly reciprocal review and integration spread context across both workflows.

This document and [roadmap.json](../curriculum/roadmap.json) define implementation order. The [44 reference definitions](../curriculum/tasks/README.md) and their catalog order/phase labels organize concept material; they are not 44 identical implementation assignments for each learner. Partial early use of a reference does not pass its deeper concepts. Detailed future issues must follow this roadmap and the task format below.

## PostgreSQL: light first, deeper with the product

A table holds rows of related records; SQL reads and changes them. A constraint is a database rule that rejects invalid data. An index helps locate rows but adds storage/write cost. A transaction groups changes into one commit or rollback; isolation controls what concurrent transactions can observe. Idempotency means repeating the same accepted operation does not apply its effect again. An outbox stores an event in the same transaction as its business change so delivery can recover later.

## Required format for a future task

1. **Product problem:** who needs the behavior and which previous capability it extends; give the learner one distinct ask and a concrete integration point.
2. **Purpose and learning:** why this belongs now, what product outcome it achieves, and plain-language explanations/examples for every named concept. Do not assume the term is already understood.
3. **Unit contracts:** for every named function, list inputs/types/defaults, success output, invalid/error output, validation order, mutation/state rules and at least one worked valid and invalid example. For async work specify cancellation, timing, freshness and recovery.
4. **Progressive hints:** three steps from a concept clue to an approach and then a diagnostic clue, without handing over the implementation.
5. **Acceptance and mastery:** observable behavior, the integrated outcome, an independent unseen variation and the coach's expected result. The two learners' asks and feature paths must differ.
6. **Frontend design:** include actual reference screen images for the web/mobile surface being built, including relevant loading, empty, error, success, offline and conflict states. Images are part of the future frontend task preparation.
7. **PR feedback:** optional suggestions for writing meaningful tests, with scenario, hint and expected behavior. Tests and documentation are not separate assigned issues; formal evidence reports and mandatory test-authoring deliverables are not substitutes for product progress.

Example of complementary contracts: Neha's parseQuantityInput(' 003 ') returns {ok:true,quantity:3}; Madhavi's validateQuantity(3) returns the same success shape but validateQuantity('3') returns {ok:false,code:'INVALID_QUANTITY'}. The former owns the form-text boundary, the latter owns the numeric domain boundary; the product composes both.

## Weekly implementation and assessment rhythm

Study the concepts and predict examples independently, then implement the distinct feature using accepted units. Integrate both branches through PRs, demonstrate the combined behavior, review the peer's decisions, and complete an unseen variation. The reviewer records per-concept evidence from the PR or session and maintains the ledgers; a separate learner-authored report is not required.

Each learner revisits an earlier basic and advanced concept weekly. Use a changed product input or failure case for retention rather than recreating an accepted feature. Assess understanding, implementation, debugging, tradeoffs and transfer at the same independent pass threshold for both learners; vary hints and challenge depth with need.

The coach predicts the expected behavior before inspecting the solution, checks it with a reproducible scenario and revises mistaken assumptions. Assess coach scenario quality as well as learner reasoning. A shared gate passes only when both learners pass.
